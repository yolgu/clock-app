# [P17] Android lifecycle 복구와 System Backup 규칙 작성

Parent plan:

- [전체 계획](../plan.md)

Status:

- In Progress

Purpose:

- reboot, app update, process removal, wall-clock/timezone 변화에서 active session을 재조정하고 transient delivery state가 Android backup으로 복제되지 않게 합니다.

Goal linkage:

- recent-app removal은 실행을 멈추지 않고 reopen이 Running을 보여야 합니다.
- reboot/update/time/timezone 변화는 재등록하되 force-stop·required permission revoke는 자동 재시작하지 않아야 합니다.
- Android System Backup은 durable Preferences/Todos만 제한적으로 허용해야 합니다.

Dependencies:

- depends_on: [[P5](P5.md), [P16](P16.md)]
- parallelizable: false

Required skills:

- [code-principles, systematic-debugging]

Boundary mapping:

- Public interface: lifecycle reason과 `DeliveryRecoveryStatus`만 Dart startup coordinator/Rhythm ViewModel에 공개합니다.
- Implementation boundary: manifest receivers가 OS event를 수신하고 headless coordinator가 Dart reconcile을 호출합니다. backup XML은 OS 데이터 범위를, startup audit은 force-stop/permission-loss 설명을 소유합니다.
- Out-of-scope adjacent behavior: 사용자 의사 없이 force-stop 해제, permission grant 직후 자동 Start, cloud sync/account, custom Android sound는 금지합니다.
- Regression scenarios: restore된 stale Alarm ID 재사용, timezone 변경 후 이전 시각 delivery, permission revoke 후 background auto-resume, system backup에 noBackup state/path 포함을 막습니다.

Files / Resources:

- Create: `android/app/src/main/kotlin/dev/wndls/clockrhythm/rhythm/{RhythmLifecycleReceiver.kt,RhythmStartupAudit.kt}`, `android/app/src/main/res/xml/backup_rules.xml`, `android/app/src/main/res/xml/data_extraction_rules.xml`, Dart `android_delivery_recovery_adapter.dart`, lifecycle/recovery tests와 physical-device checklist.
- Modify: `AndroidManifest.xml`의 `BOOT_COMPLETED`, `MY_PACKAGE_REPLACED`, `TIME_SET`, `TIMEZONE_CHANGED`, exact-alarm permission state receiver declarations 및 backup attributes; startup coordinator와 Rhythm ViewModel.
- Test: process kill/recent removal/reopen, reboot/update, manual time/timezone, permission revoke/grant, force-stop marker, D2D/cloud include/exclude inspection.
- Delete: broad default Android Auto Backup 규칙과 transient state가 normal backup path에 있으면 제거합니다.

Difficulty:

- 🔴 High

Risk:

- OS broadcast 원인과 user force-stop/permission revoke를 같은 recovery path로 처리하면 사용자가 중단한 delivery가 조용히 재활성화됩니다.

Rollback:

- lifecycle reason별 handler를 feature flag 없이 독립 경로로 유지합니다. 특정 automatic reconcile이 안전하지 않으면 그 receiver를 manifest에서 제거하고 foreground audit만 남기며 stale alarm/state를 취소합니다.

Completion criteria:

- [ ] recent-app removal/Flutter process death 뒤 native alarm과 no-backup session이 유지되고 reopen이 실제 registration을 audit해 Running snapshot을 복원합니다.
- [ ] reboot, package replacement, wall-clock/timezone change는 active+permitted session만 headless Dart로 다시 계산하고 이전 alarms를 revision 단위로 교체합니다.
- [ ] permission revoke는 alarms를 취소하고 `needsUserRecovery`를 남기며 자동 재시작하지 않습니다. grant broadcast도 Start하지 않고 다음 foreground에 안내/action만 제공합니다.
- [ ] force-stop 뒤 첫 foreground는 persisted active intent와 실제 registration 불일치를 감지해 설명·명시적 Recovery/Start를 제공하고 스스로 Running으로 바꾸지 않습니다.
- [ ] Android System Backup은 Preferences/Todos DB만 D2D와 client-side-encrypted cloud에 포함하고 session, scheduled IDs, permission, diagnostics, device paths, draft/window state를 제외합니다.
- [ ] release 앱은 account, analytics, remote crash report, application-originated network request를 만들지 않습니다.

TDD / Validation steps:

1. Failing probe or failing test:
   - Command/check: lifecycle reason table unit tests와 API별 backup XML 검사, emulator broadcast harness를 먼저 실행합니다.
   - Expected before implementation: receiver/backup rules 부재 또는 모든 reason을 자동 resume하는 잘못된 결과로 실패합니다.
2. Minimal implementation:
   - Action: reason enum/decision table → receiver/headless call → startup audit → backup allowlist 순으로 작성합니다.
3. Passing verification:
   - Command/check: Dart/Kotlin tests, API 24/31/33/36 emulator lifecycle script, `adb shell bmgr`/backup inspection이 지원되는 환경의 include/exclude 확인.
   - Expected after implementation: 각 OS event가 결정표와 같은 registration/session/result를 만들고 transient file은 restore되지 않습니다.
4. Regression lock:
   - reason decision table, manifest/backup XML snapshot, physical checklist가 automatic vs user-mediated recovery 경계를 잠급니다.

Notes:

- Android System Backup과 Portable Backup은 서로 다른 UI·문서 용어를 사용합니다.
- exact permission API가 없는 API 24–30에서는 해당 capability가 granted로 간주되지만 notification/channel 정책은 각 API 수준에 맞게 검사합니다.
